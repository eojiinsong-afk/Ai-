# 데이터 보존 원칙

> 코드를 고치기 전에 읽습니다. **기능보다 데이터 보존이 우선합니다.**
> 답사는 다시 갈 수 없는 경우가 많고, 철거된 건물의 사진은 대체할 수 없습니다.

## 1. 코드와 데이터의 분리

앱 코드(HTML/JS/CSS)와 사용자 데이터(저장소 문서)는 서로 다른 곳에 있습니다. 코드를 배포하는 행위는 데이터를 건드리지 않습니다.

- 배포 = **같은 Artifact URL 에 다시 게시**. 저장소는 그 게시와 무관하게 남습니다.
- ⚠️ **새 Artifact 로 게시하지 말 것.** 새 Artifact 는 새 빈 저장소를 갖습니다. 다른 대화에서 수정할 때는 반드시 기존 URL 을 지정해 갱신합니다.
- 저장소가 지워지는 경우는 Artifact 자체를 삭제할 때뿐입니다.
- 로컬 개발(`npm run dev`)은 계정 저장소에 접근할 수 없어 IndexedDB 를 씁니다. 실험이 실제 답사 데이터에 닿지 않습니다.

## 2. 영구 고유 ID

프로젝트·사진·기록·참조지점·사용자정의필드는 생성 시 `crypto.randomUUID()` 로 ID를 받습니다.

- ID는 문서 키이자 상호 참조 키입니다. 사진과 기록은 `pid` 로 프로젝트를 가리킵니다.
- **어떤 경우에도 재발급하지 않습니다.** 이름·주소·좌표·분류가 모두 바뀌어도 같은 프로젝트입니다.
- 백업을 복원해도 원래 ID를 그대로 씁니다. 그래서 같은 데이터를 두 번 복원해도 중복이 생기지 않습니다.

## 3. 쓰기 규칙 — 모르는 필드도 지우지 않는다

저장은 **불러온 문서 객체 전체를 되쓰는(set)** 방식입니다.

```js
// 문서를 통째로 읽어 → 필요한 값만 바꾸고 → 통째로 되쓴다
p.aptFloors = 5;
await saveProject(p);   // p 안의 다른 모든 필드(모르는 필드 포함)가 함께 보존된다
```

덕분에 최신 버전이 추가한 필드를 구버전 코드로 열어 저장해도 그 값이 살아남습니다. 문서를 새로 조립해서 쓰는 코드(`{a, b, c}` 만 담아 set)는 만들지 않습니다.

## 4. 마이그레이션

`SCHEMA_VERSION`(저장 구조)과 `APP_VERSION`(화면·기능)은 별개입니다. UI만 바뀌면 `SCHEMA_VERSION` 은 그대로 둡니다.

```js
const MIGRATIONS = [
  { v: 3, name: '무엇을 하는지 한 줄로',
    async run(store, ctx) {
      let n = 0;
      for (const p of ctx.projects) {
        if (p.newField === undefined) {        // 비어 있을 때만
          p.newField = '기본값';
          await store.put('projects', p.id, stripId(p));
          n++;
        }
      }
      return n;                                 // 변경한 문서 수
    } }
];
```

지켜야 할 것:

- **채우기만 한다.** 비어 있는 필드에 기본값을 넣는 것만 허용합니다.
- 기존 값 덮어쓰기, 필드 삭제, 문서 삭제 **금지**.
- 실행 직전 프로젝트·필드·참조지점 스냅샷을 `snapshots/premigrate_v{n}` 에 남깁니다(사진 원본 제외 — 문서 크기 한도 때문).
- 실패하면 그 지점에서 멈추고 버전을 올리지 않습니다. 다음 실행에서 다시 시도합니다.
- 저장된 데이터가 코드보다 최신이면(구버전 코드로 접속) 마이그레이션을 **실행하지 않고** 읽기만 합니다.
- 실행 이력은 설정 → 데이터 안전에 표로 남습니다.

이름을 바꾸고 싶을 때도 옛 필드를 지우지 않습니다. 새 필드에 값을 복사하고, 화면은 새 필드를 읽되, 옛 필드는 그대로 둡니다.

## 5. 삭제

- 프로젝트 "삭제"는 **휴지통 이동**입니다. 사진·답사 기록은 그대로 남고, 복원하면 함께 돌아옵니다.
- 실제 파기는 휴지통의 "완전 삭제" 한 곳에서만, 확인을 거쳐 일어납니다.
- 백업 복원은 항상 병합이며 기본값은 "겹치는 항목은 기존 데이터 유지"입니다.
- 무결성 점검은 **읽기 전용**입니다. 고아 문서를 발견해도 자동으로 지우지 않습니다.

## 6. 저장소 한계

| | |
|---|---|
| 문서 1건 | 256 KB — 사진은 자동으로 235 KB 이하로 압축 |
| 아티팩트당 문서 수 | 5,000 — 사진 1장이 문서 2개(메타+원본)를 씁니다 |

프로젝트 100건 × 사진 20장이면 문서 약 4,100개입니다. 이 규모에 가까워지면 오래된 원본을 백업으로 내보내고 앱에서는 정리하는 운용이 필요합니다.

## 검증

`npm run build` 후 브라우저에서 확인한 시나리오(2026-09-06):

1. 프로젝트·사진·기록 생성 → 저장소 메타를 구버전으로 되돌림 → 재로딩(= 코드 업데이트 직후 상황)
   → 프로젝트 유지, ID 동일, 사진 원본·기록 유지, **앱이 모르는 필드까지 유지**, 마이그레이션 v1·v2 정상 실행.
2. 휴지통 이동 → 복원 → 사진 그대로 복귀.

저장 구조를 건드리는 변경을 했다면 이 두 가지를 다시 확인하고 배포합니다.

### v1.2.0 (2026-09-06)

`SCHEMA_VERSION` 은 2 그대로입니다. 저장 구조를 바꾸지 않았습니다.

- 철도 노선은 기존 `facilities` 컬렉션에 `path` 를 가진 문서로 들어갑니다. `path` 는 v1.1.0 부터 이미 읽히던 필드라 새 마이그레이션이 필요하지 않습니다.
- 입면 선 편집·PPTX·필터는 모두 읽기 전용 계산이며 저장 문서를 만들지 않습니다.
- 헤드리스 브라우저로 확인: 프로젝트 3건 + 참조지점 6건(역·터미널·시장·현재노선·과거노선) 생성 → 거리 계산에 노선이 포함되는지, 필터 결과, 정적 지도 이미지 생성, 슬라이드 16장 pptx 생성(`python-pptx` 로 열어 표·그림 확인), 입면 보정과 선 연산 6종, DXF·PDF 출력, 노선 그리기 시작/취소 — 콘솔 오류 없음.

### v1.3.0 (2026-09-06)

`SCHEMA_VERSION` 은 여전히 2 입니다.

- 가져온 항목에는 `src{batch,file,crs,at}` 필드가 붙습니다. 문서에 필드를 **더하기만** 하므로 마이그레이션이 필요 없고, 이 필드를 모르는 구버전 코드로 열어 저장해도 3절의 되쓰기 규칙에 따라 그대로 보존됩니다.
- 가져오기는 새 문서를 만들 뿐 기존 문서를 지우거나 덮어쓰지 않습니다. 같은 자리(40m)의 같은 종류는 건너뜁니다.
- 묶음 되돌리기(`deleteBatch`)는 **그 배치로 들여온 문서만** 지웁니다. 직접 입력한 지점은 건드리지 않고, 프로젝트로 들여온 것은 휴지통으로 보내 사진·기록이 함께 보존됩니다.
- 헤드리스 브라우저로 확인: EUC-KR CSV · UTF-8 BOM CSV(UTM-K) · Shapefile 점(구 중부원점 Bessel, .prj/.cpg 포함) · Shapefile 폴리라인(UTM-K) · GeoJSON · ZIP(deflate) 여섯 가지를 가져와 좌표·인코딩·속성이 맞는지, 같은 파일을 두 번 가져와도 중복이 생기지 않는지, 묶음 되돌리기가 그 배치만 지우는지 확인했습니다. 좌표계는 pyproj 와 10개 × 6지점을 대조해 최대 오차 7mm.

### v1.5.0 (2026-09-06)

`SCHEMA_VERSION` 은 2 그대로입니다. 저장 구조를 바꾸지 않았습니다.

사진 업로드가 조용히 일부만 저장되던 문제를 고쳤습니다. 데이터 보존 관점에서 중요한 변경입니다.

- 이전에는 한 장이 실패해도 마지막에 «요청한 장수만큼 추가했습니다» 라고 알려, **빠진 사진을 알아챌 방법이 없었습니다.** 이제 실제 성공 수를 알리고, 실패한 파일과 원인을 표로 보여줍니다.
- 일시적인 저장 거절은 `putRetry` 로 최대 4번까지 다시 시도합니다(프로젝트·기록·참조지점 저장도 같습니다).
- 원본만 저장되고 메타 저장이 실패하면 원본을 지웁니다 — 갤러리에 보이지 않는 반쪽 문서를 남기지 않습니다.
- 헤드리스 브라우저로 48장 업로드를 세 조건에서 확인했습니다: 정상(48/48), 저장소가 3번에 1번 거절(재시도로 48/48 복구), 도중부터 문서 한도 초과(20장 저장·28장 실패를 정확히 보고, 고아 원본 0). 오류 분류는 13가지 문구로 단위 검증했습니다.

### v1.6.0 (2026-09-06)

`SCHEMA_VERSION` 은 2 그대로입니다. 기본 항목 `basementFloors`(지하 층수)를 **더하기만** 했으므로 마이그레이션이 필요 없습니다.

- 이전에 만든 프로젝트에는 이 항목이 빈 값으로 나타납니다. 값을 채워 넣기 전까지 문서에는 키 자체가 없고, 3절의 되쓰기 규칙에 따라 다른 필드는 그대로 보존됩니다.
- `totalFloors` 의 이름표만 «전체 층수» → «지상 전체 층수» 로 바꿨습니다. 키는 그대로이므로 저장된 값에 영향이 없습니다.
- 헤드리스 브라우저로 확인: 지하층 개념이 없던 시절의 문서(앱이 모르는 필드를 함께 넣어 둔 것)를 열어 지하층을 입력해 저장했을 때 **모르는 필드가 그대로 남는지**, 지하가 없는 사례는 빈 값으로 표시되는지, 표·필터·보고서·PPTX·CSV·마커 쪽지에 모두 반영되는지 확인했습니다.
